# API Reference

Status: **every route in this document exists** — AIG 21 milestones 11 through
15, issues 25, 28 and 32. Interactive documentation is generated by the appliance
that serves it, so what is listed here and what is running cannot disagree for
long.

Interactive documentation is generated by FastAPI at `/docs` and
`/openapi.json` on a running appliance. Nothing in this directory is a schema;
this page is the parts a schema cannot express — which responses are fragments,
what each SSE frame means, how a caller authenticates, and what fails.

`/docs` is public, and the administrative routes are listed in it. A document that
hid them would not make them safe and would make the guest API undiscoverable by
someone deciding whether to write against it; the protection is the session, and
the OpenAPI file is the shape of the thing you are already able to knock on.

## Conventions (fixed by SAPRS Chapter 10 and AEP 21)

- The JSON API is versioned under `/api/v1/...`. Additive changes only within a
  major version; removals need a major bump and migration notes in the changelog.
- Errors use one envelope for every failure, on every route:

  ```json
  {"error": {"code": "queue_full", "message": "the queue is full", "details": {"limit": 200}}}
  ```

  `details` is present when the failure has something to say and empty otherwise;
  `code` is stable, `message` is not (translate it in the template, log it, never
  parse it).
- Timestamps are RFC 3339 in UTC; durations are integer milliseconds.
- Guest endpoints require no authentication and never accept or return guest
  identity (ADR-007). A request that carries a cookie is treated exactly like one
  that does not.
- Administrative endpoints require one session cookie, described in
  [Administrator](#administrator). There is no API key, no bearer token and no
  per-guest credential: the appliance has one administrator, and ADR-007 is why
  the number of credentials is one rather than one-per-device.
- HTML fragment endpoints for HTMX are distinct from the JSON API; a fragment is
  not an API, and a fragment is what a browser's `Accept: text/html` gets.
- Everything that can change is served with `Cache-Control: no-store`, including
  error responses. The one exception is `/static`, mounted with `StaticFiles`
  defaults: fingerprinted asset URLs belong to the installer (milestone 15), and
  inventing a cache-buster here would be a second place to decide the version.

### Content negotiation

The same routes answer two kinds of caller, decided by the `Accept` header and by
htmx's `HX-Request`:

| Caller | Sends | Gets |
| ------ | ----- | ---- |
| Browser, first arrival | `Accept: text/html,...` | the full page shell |
| Browser, htmx swap | `HX-Request: true` | the fragment only, `HX-Boost`-friendly |
| Tool, script, test | `Accept: */*`, or anything without `text/html` | JSON |

`*/*` counts as a tool rather than a browser on purpose: a browser names
`text/html` because it is about to render it, and `curl` asking for `*/*` wants
the machine interface it used to have to reach `/api/v1` for.

## Guest pages

Full HTML documents. A guest who types a URL or reloads gets these.

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `GET` | `/` | Now Playing and Up Next |
| `GET` | `/search?q=` | One search box, three lanes (FTS5) |
| `GET` | `/artists` | Artists, paged (`?offset=`, `?limit=`) |
| `GET` | `/artists/{id}` | One artist: their albums and tracks |
| `GET` | `/albums/{id}` | One album: its cover and running order |
| `GET` | `/queue` | The whole waiting list |
| `GET` | `/artwork/{kind}/{id}` | Cached artwork, or a placeholder that says so |

`kind` is `album`, `artist` or `song`. An artwork miss is two different answers,
because they are two different facts: a library that depicts nothing for that
album returns `200` with a drawn placeholder; a library whose row names a file the
cache has lost returns `404` with `not_found`. A single "grey cover" answer for
both would hide a broken install.

## Fragments (HTMX)

Same data, no page shell, `Cache-Control: no-store`, and the only place a
template is reached directly.

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `GET` | `/fragments/player` | Now Playing and Up Next together |
| `GET` | `/fragments/now-playing` | The row on the speakers |
| `GET` | `/fragments/up-next` | The queue, waiting |
| `GET` | `/fragments/alerts` | The health and status strip |
| `GET` | `/fragments/search?q=` | Search results list |
| `GET` | `/fragments/artists/{id}` | Artist screen body |
| `GET` | `/fragments/albums/{id}` | Album screen body |
| `POST` | `/queue` | The guest button: `?song_id=`, a form field, or a JSON body |

`POST /queue` is **not idempotent** (SAPRS 10.4): every call appends, and a
duplicate press is a duplicate song, which is what a room expects from a jukebox.
The response is the Up Next fragment plus a confirmation naming the song and
where it went — "Playing now", or "Added at 3" — and the wording comes from the
queue item's status, never from whether the appliance happened to be busy.

## JSON API

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `GET` | `/api/v1/search?q=` | Songs, albums, artists, plus `truncated` |
| `GET` | `/api/v1/artists` | Artist list (`?offset=`, `?limit=`, capped at 200) |
| `GET` | `/api/v1/artists/{id}` | Artist, albums, tracks |
| `GET` | `/api/v1/albums/{id}` | Album and tracks |
| `GET` | `/api/v1/songs/{id}` | One track, labelled |
| `GET` | `/api/v1/queue` | `now_playing` (object or `null`), `up_next` (list), `length` |
| `POST` | `/api/v1/queue?song_id=` | Queue a song; `201` with the item's position |
| `GET` | `/api/v1/playing` | State, position, duration, fraction, wait |
| `GET` | `/api/v1/health` | Aggregate and per-component health |
| `GET` | `/api/v1/info` | Version, library counts, configured limits, `url` |

Queue entries in JSON carry the song's labels inline (`artist`, `album`) because
a client that has to make a second request per row to print a name is a client
that will get them wrong under load.

## The QR code

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `GET` | `/qr` | The printable page: the code, the address in text, and the port |
| `GET` | `/qr.svg` | The code alone, as SVG, for anything that embeds rather than opens |

Both are **public** and both are **cached** (`public, max-age=86400`), which is the
only place in Encore where a dynamic response is cacheable, and the reason is on
`docs/adr/ADR-015`: a code is immutable until an operator edits `server.domain` and
restarts, and `no-store` would have every phone in the room re-request an SVG while
somebody is looking for a wall. The address is public already — it is in the footer
of every guest page and in `/api/v1/info` — so printing it discloses nothing, and
behind the session cookie it would be a code only the operator can print.

There is no `?url=` and there never will be. A QR endpoint that encoded a
caller-supplied string is an appliance that will print a phishing code about itself.

What the code says is `ServerConfig.guest_url`, the one expression of "where a guest
points their browser": the port is included whenever it is not 80, so an appliance on
8080 prints `http://jukebox.home.arpa:8080` and not a code that resolves and refuses
the connection. `tests/integration/test_qr_routes.py` reads the URL back out of the
SVG's `<desc>` rather than calling the same helper the route calls, because the bug
this guards was four files each formatting the address correctly on their own.

## Events (SSE)

`GET /events` — one connection per screen, `text/event-stream`, `no-store`, and
`X-Accel-Buffering: no` so a reverse proxy does not hold the party in a buffer.

Three kinds of frame share the stream, and their names say which is which:

| Frame name | Body | Meaning |
| ---------- | ---- | ------- |
| `snapshot` | JSON | The whole current state. Sent first, on every connection, always. |
| `SongQueued`, `SongStarted`, `SongFinished`, `QueueAdvanced`, `PlaybackRecovered`, `LibraryReloaded`, `BuildCompleted`, `HealthChanged` | JSON, the event's own fields | A fact. Named by its class, so a ninth event type arrives with a name nobody chose by hand. |
| `progress` | JSON | Position within the current track, once a second, whether or not anything happened. |
| `swap:player`, `swap:alerts` | HTML | A region's new markup, already rendered once for all clients. |
| `resync` | empty | "You missed something; here is a `snapshot`." Sent when a stream stalls. |

`Last-Event-ID` is accepted and ignored: recovery is a fresh `snapshot`, which is
simpler and harder to get wrong than replay (SAPRS 10.5). Facts and regions are
separate frames by design — a JSON client that understands `QueueAdvanced` should
not have to parse HTML, and a screen should not be waiting on a database the
browser cannot see. A frame is never sent to one client and not another; a client
that cannot keep up (32 frames pending) is closed and rejoins with a snapshot.

### Region map

Which fact invalidates which region, as `encore/api/fragments.py` declares it:

| Fact | Regions redrawn |
| ---- | --------------- |
| `SongStarted`, `SongFinished`, `QueueAdvanced` | `player` |
| `PlaybackRecovered`, `HealthChanged` | `alerts` |
| `LibraryReloaded` | `player`, `alerts` |
| `SongQueued`, `BuildCompleted` | none yet — seen, and deliberately unwired |

Administrative regions are not in this table and are not frames. A panel under
`/admin` refreshes by fetching its own HTML when the live script reports a fact
(it dispatches `encore:change` on `document.body`), which keeps the guest stream's
budget exactly what it was before the console existed: forty phones and one
laptop, and the phones are not asked to carry a screen nobody in the room is
looking at.

## Errors

| Status | Code | Raised when |
| ------ | ---- | ----------- |
| `400` | `invalid_request` | A malformed request the router understood enough to reject |
| `401` | `unauthorized` | An administrative route with no session, or an expired one (`details.login`) |
| `403` | `forbidden` | A state-changing request whose `Origin` names another site |
| `404` | `not_found` | A path, or a library row, that is not there |
| `404` | `song_not_available` | A queue request for a song the library does not have |
| `405` | `method_not_allowed` | A guest who reloaded a POST-only URL |
| `409` | `queue_full` | The configured ceiling was reached (`details.limit`) |
| `422` | `invalid_request` | Body or query failed validation (`details.fields`) |
| `500` | `internal` | A fault. Logged in full, explained in none |
| `503` | `not_ready` | The appliance thread is not up yet |
| `503` | `search_unavailable` | The FTS index cannot answer |

`song_not_available` and `not_found` are different codes for the same status
because the second is a typo in a URL and the first is a queue that will never be
filled; an operator reading a log wants to know which.

`404` on a library miss and `409` on a full queue both leave the queue exactly as
it was: a refused request is not a partial one.

How a failure reaches a caller is a second axis, and it is the one that surprises
people: the same exception is a JSON envelope for a tool, a page inside the shell
for a browser that typed a URL, and a *fragment* for an HTMX swap. All three are
the same status and the same `code`, and a client that wants to branch should read
those two and not the markup. The exception is the `401` an HTMX panel gets, which
is a fragment **and** an `HX-Redirect` to the sign-in page: a region cannot sign
itself in, and htmx navigates on that header before it decides what to do with a
body. See [Frontend → htmx, used narrowly](../Developer/Frontend.md#htmx-used-narrowly)
for the client side of that, which is a rule in `encore-live.js` rather than a
promise in this file. A failure that swaps into an HTMX region also carries
`HX-Reswap: innerHTML`, because a fragment that replaced a self-refreshing region
`outerHTML` would take its `id` and its trigger with it: the error would be
visible once and the panel would never redraw again.

## Latency

Targets are SAPRS 1.8's; the numbers are `tests/performance/test_http_latency.py`
measured on the ARM64 development machine, untraced, and a Raspberry Pi 4 is
allowed to be slower on its own terms:

| Operation | Target | Measured p95 |
| --------- | ------ | ------------ |
| Search (`GET /search?q=`) | 100 ms | 20.7 ms |
| Queue mutation (`POST /queue`) | 50 ms | 37.6 ms |
| Navigation fragment | 200 ms | 10.0 ms |
| Administrative page | 200 ms | 16.5 ms (dashboard) |
| Playback start (appliance's part) | 250 ms | see `test_runtime_latency.py` |
| SSE propagation (fact → 40 screens) | 1 s | 0.83 ms per screen |

An administrative page pays one extra cost a guest never does — the session
lookup — and it is a dictionary probe, not a hash verification: the password hash
is computed once at sign-in, which is why a `curl`-driven script does not multiply
the number of bcrypt operations this appliance performs per second. The
administrative figures above are the four `--run-slow` budgets in
`tests/performance/test_http_latency.py`; the guest figures are the same file.

### Added after #25

The remaining codes are the administrative ones, and one of them is not a status
the guest surface can ever produce:

| Status | Code | Raised when |
| ------ | ---- | ----------- |
| `409` | `credential_exists` | A first-run `POST /admin/login` against an appliance that already has a password |
| `422` | `weak_credential` | A new password shorter than `MIN_PASSWORD_BYTES` (10 characters, `admin_service.py`) |
| `422` | `invalid_request` | A form field or query parameter that failed validation (`details.fields`) |
| `429` | `rate_limited` | Five failed sign-ins inside one window (`details.retry_after_seconds`, and a `Retry-After` header) |
| `503` | `library_unavailable` | A library reload refused the file; the running library is unchanged |

`library_unavailable` is the interesting one, because it is the only failure in
this table that leaves the appliance working: the verification happens on the new
handle before anything is swapped, so a build interrupted mid-write refuses the
button and the party continues on the catalogue it had.

The `429` is the only one that says *when*. `details.retry_after_seconds` is the
window that remains and `Retry-After` is the same number in the header a proxy or a
`curl --retry` will obey, because a wait written only in a body is a wait that gets
ignored. It is counted for the appliance rather than per address, so a locked box
answers `429` to everyone including whoever has the right password; the five
failures that caused it are in the log tail, without an address attached (ADR-007).

## Administrator

One credential for the whole appliance, and one cookie that presents it (ADR-013).
The only setting is `admin.session_minutes`; the section cannot hold a password,
because `extra="forbid"` makes a `password:` key in `encore.yaml` a startup error
rather than a false sense of security (SAPRS 12.6, AEP 17).

### The session

| Attribute | Value | Why |
| --------- | ----- | --- |
| Name | `encore_admin` | |
| Value | 32 random bytes, hex | Not derived from the password, and not stored anywhere the password is |
| `HttpOnly` | set | An injected script cannot read it; there is no client-side code that needs to |
| `SameSite` | `Strict` | This *is* the cross-site defence. There is no CSRF token, and the ADR argues that a token would be a second mechanism to keep in sync with the one the browser already enforces |
| `Secure` | not set | The appliance serves plain HTTP on a LAN (SAPRS 13.1). Setting it would make the interface unreachable rather than safer, which is the trade the ADR records rather than hides |
| `Max-Age` | `admin.session_minutes × 60` | Sliding: a request from a live session extends it, so an operator in the middle of a queue does not fall out of the console |

A session lives in memory. Restarting the appliance signs everyone out — that is
the intended behaviour, and the reason it is not stored in `runtime.db` is written
down in ADR-013. Changing the password ends every session, including the one that
asked. Signing out ends one.

State-changing requests are also refused when an `Origin` header names a site
other than the appliance (`403`). A request with *no* `Origin` is accepted, which
is what keeps `curl` working: the header is what a browser adds and a script does
not.

A person and a tool are answered differently when there is no session, and both
answers are the same fact:

| Caller | Sends | Gets |
| ------ | ----- | ---- |
| Browser following a link | `GET`, `Accept: text/html` | `303` to `/admin/login?next=<path>` |
| htmx panel refresh | `HX-Request: true` | `401` with the error fragment, which says "sign in again" |
| Tool, script, test | anything without `text/html` | `401` with the JSON envelope |

### Routes

Every path below requires a session except the two on the sign-in page.

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `GET` | `/admin/login` | The door, or the first-run form when no password exists yet |
| `POST` | `/admin/login` | `password=` — creates the credential on a fresh appliance, exchanges it for a session on every other one |
| `GET` | `/admin` | Redirects to the dashboard |
| `GET` | `/admin/dashboard` | What is playing, what is waiting, whether it is well |
| `GET` | `/admin/queue` | Every request, uncapped, with what an operator can do to it |
| `GET` | `/admin/health` | The aggregate and each component's own words |
| `GET` | `/admin/statistics` | Counters today and ever, the last fortnight, the leaderboard |
| `GET` | `/admin/logs` | The appliance's own records, newest first (`?level=`, `?limit=`) |
| `GET` | `/admin/configuration` | The validated configuration, redacted, read-only |
| `GET` | `/admin/library` | Provenance and counts, from `library.db` itself |
| `GET` | `/admin/password` | The form, and the last sign-in timestamp |
| `POST` | `/admin/playback/{command}` | `pause`, `resume`, `skip`, `stop`, `start` |
| `POST` | `/admin/queue/clear` | Every waiting request out; the current track stays |
| `POST` | `/admin/queue/{item_id}/remove` | One request out; removing what is playing is a skip |
| `POST` | `/admin/library/reload` | Reopen `library.db`, and tell every screen it changed |
| `POST` | `/admin/password` | `current=`, `new_password=` — replaces the password and ends every session |
| `POST` | `/admin/logout` | Ends this session and withdraws the cookie |

A `POST` from a browser with no JavaScript gets a `303` back to the page it came
from; an `HX-Request` gets the panel that asked, redrawn, with one sentence about
what happened (`?panel=` names the region). Both perform the command — the shape
of the bug that `tests/regression/test_issue_28_administration_interface.py`
exists to keep dead.

### From the JSON API

Two administrative routes sit under `/api/v1` rather than beside the pages, for
the reason SAPRS 10.2 gives (an operator scripting a shutdown should not have to
drive a browser), and they take the same session:

| Method | Path | Purpose |
| ------ | ---- | ------- |
| `DELETE` | `/api/v1/queue/{item_id}` | `removed`, `as` (`skip` or `removal`), `queue_length`, `state` |
| `GET` | `/api/v1/stats` | The statistics page's report, as data |

```console
$ curl -s -c /tmp/encore.jar -d 'password=…' http://encore.local/admin/login -o /dev/null
$ curl -s -b /tmp/encore.jar http://encore.local/api/v1/stats
{"totals": {"plays": 41, "searches": 96, …}, "today": {…}, "trend": […]} \
  | jq '.totals.plays, .generated_at'
$ curl -s -b /tmp/encore.jar -X DELETE http://encore.local/api/v1/queue/7
{"removed": 7, "as": "removal", "queue_length": 2, "state": "playing"}
```

The cookie is the only credential a tool needs, and no route accepts the password
itself — an endpoint that took a password per request would be a rate limiter
waiting to be written and a hash verification in the middle of every p95.

`GET /docs` and `/openapi.json` are public. Administrative routes appear in them;
they still require the session, and a document that hid them would make the guest
API undiscoverable in exchange for nothing.
